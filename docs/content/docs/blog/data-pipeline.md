# 《数据的复杂采集、脱敏、归一与向量化》

TJUClaw 的数据处理链路最终演进为以下形态：`tjuclaw-crawler` 负责持续抓取公开数据，将帖子、正文、元数据、链接等结构化或半结构化内容写入 PostgreSQL，同时将 PDF、PPT、DOCX、图片等原始文件转存至 对象存储。在抓取过程中，系统会将外部链接推入调度队列进行深度递归抓取，而非仅在首层页面停止。

数据入库后，首要任务是隐私脱敏。我们通过程序化规则精准识别姓名、手机号、学号、邮箱等个人信息（PII）并进行掩码处理，确保数据在进入 AI 链路前完成净化。随后，数据库中的结构化数据可直接进入归一化流程；而存储在 对象存储 中的扫描件、文档等非结构化文件，则交由 PaddleOCR-VL 1.6 进行文档解析，将各类异构文件统一转化为初步的 Markdown 格式。

然而，拿到 OCR 输出的 Markdown 并不意味着数据已经处于可用状态。在机器解析过程中，原始文件中的复杂公式和表格结构极易发生破损、错位或信息丢失。因此，我们在 PaddleOCR-VL 之后引入了第二层处理：将这些包含受损结构或排版杂乱的粗略 Markdown，连同已结构化的数据，统一交由 Qwen3.7-Flash 进行语义层面的修复与格式归一化。模型不仅会将它们重塑为系统定义的标准 Markdown 结构，还会依靠语义上下文对破损的表格与公式进行逻辑校准。至此，无论一条知识最初是数据库中的一行记录、一篇网页正文，还是一份数十页的 PDF，在下游看来，它都已经变成同一种介质：经过脱敏且结构稳定的 Markdown 文档。

接下来，这些标准 Markdown 会通过 WeKnora Connector 持续注入至 WeKnora。系统在知识库侧完成解析、分块（Chunking）与索引构建，内容处理与 Embedding 环节均采用千问系列模型，最终将文档转化为可供语义检索的向量表示。在此，我们并未让业务后端直接操作向量数据库，而是将知识检索抽象为一个独立工具：TJUClaw 后端负责接收查询、调用 WeKnora 并整理召回结果，最终通过 `tjucli` 暴露给运行在腾讯云 Agent 沙箱中的 $\pi$ agent。

因此，从 Agent 的视角来看，复杂的底层逻辑被完全屏蔽。它只需在沙箱中执行一次简单的命令调用：

```bash
tjucli knowledge search "软件工程培养方案"
```
即可获取经过检索与重排的高质量上下文。

但在这一行命令背后，实际串联的是一条极具深度的流水线：

```text
公开数据
    ↓
tjuclaw-crawler
    ↓
PostgreSQL / 对象存储
    ↓
PII 脱敏
    ↓
PaddleOCR-VL 1.6 (文档解析，伴随结构损耗)
    ↓
粗糙 Markdown
    ↓
Qwen3.7-Flash (语义修复与归一)
    ↓
规范化 Markdown
    ↓
WeKnora Connector
    ↓
Chunking / Qwen Embedding
    ↓
向量知识库
    ↓
TJUClaw Backend
    ↓
tjucli (工具抽象)
    ↓
Tencent Cloud Agent Sandbox
    ↓
pi agent
```

换言之，我们的终极目标并非构建一个“支持文档搜索的网站”，而是将形态各异、质量参差且夹杂隐私的原始数据，逐步压缩、提纯为 Agent 可以直接消费的知识接口。

这也是为什么我们认为，仅仅将 PDF 丢给 Embedding 模型并存入向量数据库，只解决了整个链路中最末端的环节。系统真正的工程壁垒，其实都建立在向量化以前：如何高效回流数据、如何妥善保管原始文件、如何处理递归抓取、如何进行可靠脱敏、如何修复破损的公式与表格、如何将数十种输入降维成一种稳定的数据表示，以及如何保障这些数据在未来依然具备可重放的处理能力。

这篇文章，我们就将沿着这条流水线逆向拆解，详细阐述我们最终是如何将这一整套复杂系统拼接落地的。

## 总体架构全景

![TJUClaw 数据采集、存储、脱敏、归一、向量化与检索全链路架构图](./images/data-pipeline-architecture.webp)

整个数据管道清晰划分为六个核心阶段，每个阶段各司其职、协同流转：

1. **01 采集 (Capture)**：面向学校官网/学院网站、论坛/帖子、公告/通知、课程资源、校内 Wiki 及外部链接，由 `tjuclaw-crawler` 进行递归爬取、发现新链接与内容调度；
2. **02 存储 (Store)**：实行结构化与非结构化数据分流存储。帖子正文与元数据、页面链接拓扑存入 **PostgreSQL**，PDF、PPT、DOCX 及图片等原始附件持久化存入 **对象存储** 对象存储；
3. **03 脱敏 (Sanitize)**：通过规则与小模型结合的隐私引擎，自动识别姓名、学号、手机号、邮箱等个人敏感信息（PII）并实施掩码与隔离；
4. **04 归一 (Normalize)**：将多模态异构数据转化为统一的规范化 Markdown。先通过 **PaddleOCR-VL 1.6** 解析文档版面生成粗略 Markdown，再经由 **Qwen 3.7 Flash** 进行语义重构与格式统一，生成标准 Canonical Markdown；
5. **05 向量化 (Embed)**：经由 **WeKnora Connector** 接入自托管知识引擎 WeKnora，采用 Qwen 模型进行内容处理与层级分块（Chunking），经由 Qwen Text Embedding 向量嵌入模型持久化至向量知识库（Vector Knowledge Base）；
6. **06 检索 (Retrieve)**：后端服务（`tjuclaw-api` / `tjucli`）向用户提供端到端问答检索与重排服务，并将检索工具标准封装给腾讯云 **Agent 沙箱** 中的 **$\pi$ Agent** 调用执行。

下面，我们顺着这六个阶段的核心工程节点，拆解其中的关键技术攻坚。

---

## 1. 采集（Capture）：动态世界里的游标、拓扑与魔数

很多人写爬虫喜欢用单进程 `for` 循环遍历列表页。这种写法在玩具项目里跑得很好，但在面对包含数万篇历史归档、上千个分类目录、动态增量更新的校园多站点时，极易因网络波动、反爬拦截或进程异常而崩溃重来。

在 TJUClaw 中，`tjuclaw-crawler` 实现了高可靠的增量采集架构：

### 游标隔离与状态持久化（Cursor Persistence）

将**状态管理**与**抓取逻辑**彻底解耦。每个数据源在 PostgreSQL 中维护自己的独立状态元组 `(source_id, cursor)`：

- **增量游标（Incremental Cursor）**：记录当前数据源最近一次处理成功的确定性指标（如主键 ID、带时区的时间戳、或分页 Token）。即使中间遇到网络波动中断，重启后直接从上次游标处继续，绝不在重复的数据上浪费请求配额；
- **指纹快照（Fingerprint Snapshot）**：对文章的更新时间、标题和正文计算 SHA-256 摘要。如果远端内容未发生实质变更，只更新存活状态（`last_seen`），直接跳过后续耗费算力的文档解析、Markdown 转换和向量化开销；
- **递归拓扑发现**：爬虫在解析页面的同时自动提取未探索的同源外链与附件引用，放入去重调度队列，实现从根站点到深层资料的全自动发现与回溯。

### 附件嗅探的三重检验：别相信文件扩展名

在采集过程中，几乎一定会遇到各种附件：PDF 公文、Word 报名表、Excel 统计表，甚至是几十兆的无意义视频文件。

最幼稚的过滤方法是判断 URL 后缀是否是 `.mp4`。但现实世界中，很多人把视频直接作为二进制流通过类似 `/download?file_id=1028` 的接口下发，或者文件扩展名被故意或无意写错（比如明明是 MP4 却写成 `.bin`，或者明明是 PDF 却写成 `.doc`）。

真正可靠的文件类型判定，必须走**三重交叉校验**：

```
[文件扩展名判断] ──> [HTTP Content-Type] ──> [文件头 Magic Number 二进制特征码]
```

例如在读取文件的前几个字节时，直接在内存切片中检查文件魔数（Magic Number）：

```typescript
// PDF 的前 4 个字节固定为 %PDF (0x25 0x50 0x44 0x46)
const isPdf = bytes[0] === 0x25 && bytes[1] === 0x50 && bytes[2] === 0x44 && bytes[3] === 0x46;

// PNG 的前 8 个字节固定为 0x89 0x50 0x4E 0x47 0x0D 0x0A 0x1A 0x0A
const isPng = bytes[0] === 0x89 && bytes[1] === 0x50 && bytes[2] === 0x4e && bytes[3] === 0x47;
```

只有通过二进制层面的格式验证，才能把危险的隐藏脚本、不需要的大体积音视频可靠地剔除在解析管道之外，避免把下载队列和下游解析器塞爆。

## 2. 存储分流（Store）：结构化与非结构化物理解耦

在爬取海量多源数据后，若把二进制附件（PDF、DOCX、PPT、图片）与元数据混合存放在单体数据库中，数据库体积会迅速膨胀，备份和迁移运维将变得极其沉重。

TJUClaw 在存储阶段实施严格的**存算与介质分流**：
- **PostgreSQL**：承载高频关系型查询，包括帖子列表、文章标题、作者、标签、发布时间戳、解析后的正文内容以及多篇文档之间的超链接关系网；
- **对象存储**：作为高可靠、零出网流量费的对象存储，专门持久化归档原始文件（Raw Files）。不论是几十兆的选课排课 PPT，还是教务处规程 PDF，均以唯一 Content-Hash 为文件名存储于 对象存储 中，下游解析流水线按需流式拉取。

## 3. 严苛脱敏（Sanitize）：保护隐私是一场与误报的博弈

在抓取公示公告、社群互动或公开资料时，经常会混入极度敏感的信息（PII，Personally Identifiable Information）：
- 18 位居民身份证号码；
- 手机号与成批量的学号、工号名单；
- 个人私有邮箱；
- 开发者误贴在代码片段或配置文件里的公网密钥（Cloud AccessKey、API Token）。

如果这些数据未经清洗直接倒进大模型的上下文或向量检索库，大模型很容易在面对“请帮我查一下某某的联系方式”这类提示时，直接把这些敏感信息当成事实给“吐”出来，造成极其严重的合规灾难。

### 身份证号识别：别只用 `\d{18}`

很多人写脱敏正则，随手就是一个 `/\d{17}[\dXx]/`。但如果你把这个正则扔到包含大量交易单号、条形码、时间戳的现实数据里，**误报率会高到令人发指**。

中国的 18 位身份证号码是有严密的国家标准算法的（GB 11643-1999，ISO 7064:1983.MOD 11-2）。前 17 位是本体码，第 18 位是根据前 17 位加权求和对 11 取模计算出的校验码：

```typescript
/**
 * 校验 18 位中国居民身份证校验码
 */
export function isValidChineseIdCard(id: string): boolean {
  if (id.length !== 18) return false;

  // 加权因子系数
  const weights = [7, 9, 10, 5, 8, 4, 2, 1, 6, 3, 7, 9, 10, 5, 8, 4, 2];
  // 校验码映射字符 (0..10 对应字符)
  const checkCodes = ["1", "0", "X", "9", "8", "7", "6", "5", "4", "3", "2"];

  let sum = 0;
  for (let i = 0; i < 17; i++) {
    const num = parseInt(id[i], 10);
    if (isNaN(num)) return false;
    sum += num * weights[i];
  }

  const remainder = sum % 11;
  const expectedCheckCode = checkCodes[remainder];
  return id[17].toUpperCase() === expectedCheckCode;
}
```

配合地址码前两位（合法的省份代码，如 `11`..`65`）和出生年份月份的范围判断，**可以将假阳性（False Positive）降低三个数量级**。

### 规则校验与大模型联合脱敏

对于格式规范的信息，规则引擎能够以极低开销完成毫秒级匹配；但对于自然语言语境中的“隐式姓名”与特定联系方式，TJUClaw 引入了小参数量模型进行语义识别：
- 姓名：`张三` $\to$ `***`
- 学号：`2024123456` $\to$ `2024******`
- 手机号：`13812345678` $\to$ `138********`
- 邮箱：`zhangsan@tju.edu.cn` $\to$ `*******@tju.edu.cn`

当单篇文档中检测到的敏感特征超出正常公布范围或命中私钥时，系统触发**隔离机制（Quarantine）**，阻断其向公开知识库的扩散，筑牢安全防线。

## 4. 格式归一化（Normalize）：双阶段多模态 Markdown 重建

如果问现代 LLM 最喜欢吃什么格式的数据，答案绝对不是纯纯的无格式 Plain Text，也不是满地括号嵌套的 JSON/HTML，而是 **Markdown**。

Markdown 的绝妙之处在于：**它在近乎零 Token 额外浪费的前提下，用最简练的文本符号（`#`、`-`、`|`、`>`）完整保留了人类长文的核心层次结构。**

在 TJUClaw 的架构中，多模态原始文件转 Markdown 采用两阶段流水线：

```
[原始附件 (PDF/PPT/图片)] ──> [PaddleOCR-VL 1.6] ──> [粗略 Markdown] ──> [Qwen 3.7 Flash] ──> [规范化 Canonical Markdown]
```

### 第一阶段：PaddleOCR-VL 1.6 物理版面与文字解析

处理复杂版面公文与多栏排版文档时，普通文本提取工具往往会出现阅读顺序横向错乱。我们采用 **PaddleOCR-VL 1.6** 进行高精度版面分析与文字识别：
- 还原表格的行列结构，将图形报表转换为 Markdown 兼容表格；
- 识别印章、抬头与双栏文本块，按正确的阅读顺序拼接；
- 剔除页眉、页脚及冗余页码干扰，输出包含基础标题标记的粗略 Markdown。

### 第二阶段：Qwen 3.7 Flash 语义理解与格式统一

粗略 Markdown 往往还残留有换行碎裂、标点不统一或标题层级不严谨等问题。为此，数据流入 **Qwen 3.7 Flash**：
- **层级规范化**：校准课程介绍、课程目标、学分说明等段落的 `#`、`##` 标题深度；
- **不可见控制字符净化**：剥离老旧打印机驱动或富文本留下的 `\x00-\x1F` 等幽灵字符，防止下游 XML 解析器崩溃（如 `PCDATA invalid Char value` 报错）；
- **时区与时间归一化**：统一将口语化时间转为标准 RFC 3339 / ISO 8601 带时区格式（`+08:00`）。

经由此流水线产出的 **Canonical Markdown**，结构紧凑且语义高度聚焦，为后续的切块与嵌入打下了最坚实的基础。

## 5. 向量化（Embed）：WeKnora 与混合检索架构

当所有五花八门的异构数据都被彻底“驯服”为格式规范、层次分明、安全干净的 Canonical Markdown 之后，后续的向量化工作便交由 **WeKnora Connector** 接入知识引擎 WeKnora。

```
[规范化 Canonical Markdown]
             │
             ▼
[Qwen 内容处理 / Chunking] ──> 严格依循 Markdown 标题树 + 注入面包屑路径
             │
             ▼
[Qwen Text Embedding 向量嵌入] ──> 生成稠密向量表示
             │
             ▼
[向量知识库 (Vector Knowledge Base)] ──> 向量空间聚类与混合索引
```

### 拥有 Markdown 后，再也不需要死板的“固定字数分块”

传统的 RAG 经常采用“每 500 字切一刀”的机械切分，这极易在条款的核心逻辑或转折句正中间硬生生切断。

**但在 Canonical Markdown 下，切块可以完全依循标题树（Hierarchical Semantic Chunking）展开：**

1. **以自然标题（Heading）为天然语义切分边界**：优先在 `##` 或 `###` 章节边界切割，保证一个业务点或章节逻辑的完整性；
2. **强制注入层级路径（Breadcrumbs Injection）**：在每一个切割后的切片最前头，自动附带上级 Markdown 标题链：
   ```markdown
   > 路径：教务管理办法 > 成绩与绩点评定 > 缓考申请条件

   学生因病无法参加期末考试的，须在考试前向开课学院提交二级甲等以上医院证明...
   ```
   即使该切片被检索出来单独喂给 LLM，大模型也能凭借第一行的路径头，一眼明白该条款适用的前置业务边界，彻底避免断章取义！
3. **保留 10%~15% 的重叠窗口（Overlap）**：为跨段落的转折逻辑提供容错缓冲。

---

## 6. 检索（Retrieve）：从后端服务到腾讯云 Agent 沙箱闭环

数据经过向量化后，最终的使命是赋能业务。在 TJUClaw 中，检索能力不仅面向常规问答，更是作为确定性工具供给智能体调用：

```
[用户提问] ──> [后端服务 (tjuclaw-api / tjucli)] ──> 检索与重排返回 Top-K
                      │
                      ▼
               [tjucli 命令行工具]
                      │
                      ▼
           [腾讯云 Agent 沙箱环境]
                      │
                      ▼
             [π Agent 执行环境]
```

1. **双路召回与重排序（Hybrid Search & Reranking）**：
   - 面对“微积分 A(1)”与“微积分 B(1)”、“54 教学楼”与“55 教学楼”等高敏编号，单纯的 Dense 向量余弦距离极难区分。后端通过 **稠密向量 (Dense)** 与 **BM25 稀疏检索 (Sparse)** 联合召回，再经由 Cross-Encoder 精排模型筛选出最精准的前 3~5 个片段；
2. **封装为 tjucli 确定性工具**：后端检索能力通过强类型 CLI 命令（`tjucli`）向外暴露，返回标准 JSON 结构与文件 SHA-256 校验哈希；
3. **交付腾讯云 Agent 沙箱与 $\pi$ Agent**：当用户在客户端下发复合任务时，运行在独立沙箱内的 $\pi$ Agent 可直接调用 `tjucli` 工具进行知识查询，在无外部污染的隔离空间内完成推理并交付可检验的最终成果。

## 7. 写在最后

数据管道就像是一座城市的地下管网，它平时深埋在系统底层，不显山不露水，没有任何酷炫的 UI 界面，甚至很少被普通用户直接感知。

但正是从 **`tjuclaw-crawler` 的游标断点抓取**、**PostgreSQL 与 对象存储 的动静分流**、**严苛的 PII 身份证算法脱敏**，到 **PaddleOCR-VL 1.6 + Qwen 3.7 Flash 的 Markdown 归一化**，再到 **WeKnora 的混合切块与腾讯云 Agent 沙箱的最终闭环**，这一套环环相扣的技术雕琢，构筑起了 TJUClaw 最核心的技术护城河。

唯有在上游把每一处脏数据洗刷干净、把每一处安全隐患严防死守，下游的智能体与大模型才能真正做到行稳致远、信手拈来。
